# Practical infrastructure learning: platform audit

**Reviewed 2026-11-03.** This audit supports Ascend's proposed practical track covering Linux servers, Internet publishing, private access, tunnels, mail, reliability, and resource planning. It extends the [DevOps curriculum research](devops-track-design.md) with the user's local-PC, small-server, and future-hardware requirements.

There are useful precedents for most parts of this track. The strongest combination in this sample is **Linux Upskill Challenge's learner-owned server, DigitalOcean's focused operational tutorials, SadServers' independent repair cases, Killercoda's versioned scenario structure, and the integrated deployment projects described by KodeKloud and TechWorld with Nana**. The sampled pages do not establish that a single offering delivers the user's entire requested sequence, particularly custom tunnels, mail operations, constrained storage, measured concurrency, and a path from one PC to multiple physical machines.

This is an evidence-backed design input, not proof that Ascend's future course improves learning or makes graduates job-ready. Those claims require working exercises, successful and failing reference runs, and learner evaluation.

## Evidence and limits

The [source ledger](local-to-internet-platform-sources.json) contains **15 first-party sources across eight candidate platforms or learning libraries**. Substantive syllabus, lesson, scenario, or technical article content was inspected for **seven**. Cisco's course title and navigation loaded, but its syllabus did not render in this session; its coverage remains explicitly unverified.

All 15 requested pages returned HTTP 200, which alone does not prove their main content was accessible. Four DigitalOcean article bodies were read after Chromium rendering because the initial HTML text extraction contained mostly the site shell. A Chromium visit to Cisco still exposed only navigation. The other substantive pages were read from retrieved HTML. The ledger records requested/resolved URLs, retrieval times, response hashes, and rendered-text hashes where used.

No paid classes were attended, accounts created, competitor labs started, deployments published, or performance results independently reproduced in this platform audit. Student testimonials, advertised outcomes, completion times, and internal grading claims remain provider statements. A separate Ascend lab proof can demonstrate a specific implementation; it cannot validate an entire curriculum by itself.

| Evidence level | What it supports here | What it does not establish |
| --- | --- | --- |
| Public lesson or article inspected | The instructions, prerequisites, mechanisms, and stated outcome are present in that version. | That every command succeeds on a different OS/version, account, or network. |
| Public syllabus/scenario description inspected | A provider describes a topic, practical format, entry level, or success check. | That the reviewer completed the exercise or that its grading cannot be bypassed. |
| Metadata/header only | The route and advertised course title exist. | Detailed curriculum, lab count, simulator use, or completion requirements. |
| Ascend design inference | A proposed teaching pattern is traceable to an inspected precedent. | Measured usability, retention, skill transfer, or infrastructure capacity. |

## Coverage of the requested capabilities

“Not established” below means the selected sources did not establish coverage. It is not an assertion that the provider has never published a relevant lesson elsewhere.

| Requested capability | Strongest inspected precedent | Coverage and remaining Ascend work |
| --- | --- | --- |
| **Linux, SSH, VPS setup, always-running service** | LUC [LUC1], [LUC2], [LUC3]; DigitalOcean initial setup [DO1]; KodeKloud prerequisites [KK1] | Strong foundational precedent. Add an explicit distinction between a process surviving a shell exit, starting after reboot, surviving host failure, and meeting an uptime target. |
| **Create VMs, host guest websites, administer a VM host, resize resources** | LUC's VM/VPS setup choices [LUC3]; KodeKloud's VirtualBox/Vagrant topics [KK1]; LF's virtualization prerequisites [LF1] | Using a guest and operating its hypervisor are distinct skills. The samples support a VM entry route but do not establish full host administration, resource resizing, quotas, or a college-style service. Add explicit create/clone/start/stop, guest networking, SSH access, storage/backup, and host-resource exercises from the chosen hypervisor's primary documentation. |
| **Publish a website; DNS/TLS; reach it from another network** | KodeKloud's prerequisite topics [KK1]; LUC's web service/network tasks [LUC1], [LUC2] | Teach listener → host firewall → LAN → router/provider → DNS/TLS → application. Require a separate client test. A listener on every interface is not proof of public Internet reachability. |
| **Cloudflared, outbound tunnels, CGNAT, custom tunnels, SSH forwards** | General SSH/networking foundations above; no complete sequence established in this sample | Add a primary-documentation-based tunnel branch. Specify whether each exercise forwards one TCP service, publishes HTTP, or routes IP traffic, and identify the relay/public endpoint required. |
| **VPN use and setup** | DigitalOcean WireGuard [DO2] | A concrete server/peer, IPv4/IPv6, key, firewall, and optional gateway sequence exists. Teach split versus full routing, DNS behaviour, endpoint reachability, and failure diagnosis; do not treat VPN connectivity as application authorization. |
| **Own mail server** | DigitalOcean Postfix [DO4] | Foundational MTA/client/local-mail work is covered. Ascend still needs a coherent SMTP submission/delivery, mailbox access, authentication, DNS, reputation, queue, backup, and abuse-prevention branch. Local mail exchange can be practised before public delivery is available. |
| **Free deployment and developer tool choices** | LUC's local setup [LUC3]; free documentation; Nana's explicit cost discussion [NANA1] | Distinguish free software, local execution, trial credits, free hosting quotas, domains, and recurring bandwidth. Provide an execution path that does not depend on an expiring credit. |
| **Load balancing and deployment failure** | HAProxy concepts [DO3]; SadServers web/container scenarios [SAD1]; Nana's recovery/pipeline projects [NANA1] | Useful precedents for routing and troubleshooting. Add bounded load tests, backend drain/recovery, session/data implications, and the load balancer's own failure. Multiple backends on one host do not survive that host failing. |
| **Concurrency, resource estimation, optimization** | SadServers resource diagnosis [SAD1]; monitoring in KodeKloud/Nana [KK1], [NANA1]; SRE framing [LF1] | An end-to-end quantitative sequence was not established from these samples. Ascend should teach measurement, workload shape, latency/error objectives, throughput, bounded queues, CPU/memory/storage/network bottlenecks, and repeatable comparisons. |
| **MicroSD and constrained-device operation** | LUC's logging/rotation and filesystem work [LUC1] | Useful foundations, but no complete microSD/4–8 GB operation track established. Add write budgets, free space/inodes, log retention, backup/restore, memory limits, power-loss behaviour, and offloading builds to the PC. |
| **PC-only first, physical devices later** | LUC Day 0 [LUC3]; server/PC/mobile peer choices in WireGuard [DO2] | Strong precedent for location-independent commands. Add explicit lessons that require real hardware observations—power, thermals, storage media, NICs/Wi-Fi—and identify what a VM can emulate versus what it cannot measure faithfully. |

## Teaching patterns to adopt

1. **Explain the mechanism, then do the smallest useful operation.** The Linux and server-setup sources make a concrete machine understandable before automation. Start with a request and its listening process, not a cloud dashboard full of unrelated controls. [LUC1], [DO1], [KK1]
2. **Keep one evolving service and topology.** Nana's public syllabus repeatedly integrates earlier artifacts into later projects. Preserve the same release, configuration, access diagram, and runbook as the learner adds remote access, publication, recovery, and capacity. [NANA1]
3. **Pair instruction with fresh diagnosis.** LUC already links a taught networking operation to independent SadServers tasks. The independent task should change the cause or constraint, rather than merely the IP/port text. [LUC2], [SAD1]
4. **State what “done” means before allocating infrastructure.** SadServers entries name a task and test; Killercoda defines an explicit step check. A practical unit needs inputs, permitted actions, observations, positive/negative checks, retained artifacts, and a cleanup/recovery step. [SAD1], [KILL2]
5. **Allow a local equivalent and state its limits.** LUC permits a local machine and explains that the commands transfer. Preserve the concepts when a learner lacks a VPS or Raspberry Pi, then add the real deployment/network/hardware evidence when that environment becomes available. [LUC3]
6. **Give practitioners fault depth and constraints.** SadServers' difficulty range and varied services support independent entry. Increase ambiguity, interacting failures, load, recovery requirements, and explanation quality; do not merely remove instructions or enlarge an instance. [SAD1], [SAD2]
7. **Teach reliability beyond a green response.** HAProxy's single-point-of-failure discussion and the SRE outline support explicit failure domains, observability, and recovery. A public URL, one 200 response, or two healthy processes alone does not establish availability or capacity. [DO3], [LF1]

The acquisition decision should be visible in every practical unit: **what runs locally, what needs another logical machine, what benefits from another physical device, and what truly requires a reachable external service or provider capability**. A local VM may fully satisfy a Linux/SSH task while only approximating an Internet routing task. Keep that difference in the evidence record without preventing the learner from studying the mechanism.

## Credibility gates for the resulting track

| Gate | Evidence required before claiming completion |
| --- | --- |
| Curriculum grounded in existing practice | A learning outcome links to an inspected source and a concrete authored exercise; marketing claims are excluded from the proof. |
| A practical exercise works | A reference run and deliberate failure run on the named OS/tool versions; commands, outputs, cleanup, and retained artifacts are recorded. |
| Hardware/resource feasibility | Measurements on the named environment, including aggregate memory, temporary disk, background services, and load-generator impact; larger-hardware options remain separately labelled. |
| Transfer across environments | At least a local reference run and the relevant different topology/host class for the skill being claimed. “Works on localhost” cannot verify public DNS, ISP traversal, power recovery, or email deliverability. |
| Beginner/practitioner usability | Learners can identify the goal, next action, save location, and finish condition without intervention, then solve a fresh case. Self-reported confidence and attendance are supplementary. |
| Sustainable operation | Real reboot/restore, credential rotation, expiry/failure handling, storage retention, and owned cleanup for the capabilities taught. |

This makes “proved” precise: the plan has a traceable instructional basis now, and each implemented capability earns narrower, reproducible evidence as it is built and piloted.
