# 05. Use physical devices well

Prepare a Pi for headless key-based administration, deploy a boot-managed service and check it from your PC; use the same software procedure in a Linux VM when no device is available.

Author estimate: 90 minutes guided practice and 120 minutes independent work; split into sessions as needed. The portable preparation alone is usually 5–15 minutes. Setup, downloads and provider approval are separate.

## Before starting

Portable model: Python 3.11+ and an editor. Choose one native route. Pi: an owned model supported by the current 64-bit Raspberry Pi OS Lite image (for example Pi 3/4/5), its correctly rated supply/cable, removable microSD/reader and an owned LAN. A 1 GiB Pi with a 16 GB card is a starting allowance for this one small Python service; inspect current OS requirements, free space and measured use rather than treating it as a capacity guarantee. A 2 GiB+ model or larger card provides more working room but is not a purchase requirement. PC/VM: supported Multipass or the earlier libvirt guest, around 1 GiB guest RAM/12 GiB disk initially, plus host reserve. The PC needs OpenSSH/scp, Python and an editor; Imager and all core software are free. One trusted console/provisioning channel is needed to authenticate the initial SSH host fingerprint; a first-use network scan alone cannot do that.

Download /training/io-resilient-hardware.zip and extract it into a NEW folder you choose on your PC. Open a terminal in its io-resilient-hardware directory; read README.md and bootstrap.md. Python 3.11+ runs the portable tools without extra Python packages. POSIX examples use Linux; Windows users can use a prepared Linux guest or WSL for the initial shell practice. Create work/ and notes/. Copy notes-template.md in your editor to notes/05.md, or append a dated attempt if the note already exists. Input files are in inputs/NN/, portable starting cases in cases/, operational instructions in lessons/NN.md, and the shared synthetic service in shared/. All generated work remains in the local paths printed by the tools. Opening a challenge does not create or upload these files. Use Ascend's notebook/upload control only when you choose to copy evidence into Ascend. Run commands one at a time on the named HOST, GUEST or CLIENT. Replace explicit address/key placeholders after inspection, and keep each foreground service in its own terminal. Stop its process with Ctrl+C before reusing the same listener.

Use only the named learner-owned environment. Commands that install packages or change services, networks, storage or VMs belong on that specified guest/host. A college-provided guest account is not permission to administer the physical host.

## How it works

Pi/ARM images, headless boot, power, cooling, Ethernet, USB storage and sleep behaviour.

A Pi, spare laptop or mini-PC can remain on while the learner PC sleeps, and supplies an independent power/storage/network failure domain. The host need not keep a VM application window open for a virtual guest to run either; the difference is whether the physical host itself stays powered and awake. A headless system boots from persistent media and obtains an address before SSH can reach its running server. Raspberry Pi Imager prepares the OS, local account and SSH configuration; it does not make a public internet route. A public user key belongs on the target, while its private key stays on the PC.

Choose the Pi or VM route below. Both run the same readable Python service and the same private SSH-forwarded client check. The VM route completes the software operation without purchasing a Pi. Only an actual device can add measurements of its supply, SD/USB storage, temperature and throttling. The portable JSON case describes a supplied Pi planning scenario; its Boolean fields must not be treated as claims that a PC user measured hardware.

For a Pi, select the exact model in the current official Imager, choose a compatible Raspberry Pi OS Lite (64-bit) image, and identify the removable card by model and capacity before writing. Writing an image erases that selected medium: retain any needed files and unplug unrelated removable disks to make the choice unambiguous. Configure hostname ascend-pi, your own non-root account, timezone and SSH with the generated PUBLIC key. Use a model-rated regulated supply; power requirements and the USB power budget differ across models. Ethernet and DHCP are a simple first boot path. If the model needs Wi-Fi, configure its permitted SSID/country privately in Imager and check peer isolation; no Wi-Fi credentials belong in notes.

Authenticate the first server fingerprint through a trusted local console or existing provisioning channel. A temporary display/keyboard can be used once, after which operation is headless. The VM route obtains the fingerprint through its owned host control plane. If a fully headless Pi has no separate trusted channel, an isolated first-use connection can be recorded as trust on first use, but leave the independently authenticated identity control incomplete until that channel is available. ssh-keyscan collects the presented key; it does not authenticate the device by itself.

Store service files under the explicit /opt/ascend-device path on the chosen target. A separate service account writes persistent application state in its dedicated data directory; the login operator uses sudo for installation and recovery. Loopback binding plus an authenticated SSH forward keeps the teaching service private. Publishing a website more widely is the separate Web Hosting route. Record the OS/Python architecture and memory/storage use; do not infer performance or power savings from core counts alone. USB SSD storage and suitable cooling can improve a later deployment, with their actual power/boot support checked first.
