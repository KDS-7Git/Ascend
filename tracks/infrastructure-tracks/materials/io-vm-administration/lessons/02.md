## How it works

Cloud images, checksums, virtual disks, firmware, cloud-init and console access.

A cloud image is a reusable operating-system disk, while cloud-init supplies each guest with its own identity and startup configuration. A template must not share private keys, machine IDs or mutable application data between users. Verify the image source/digest, create a separate writable disk, and preserve console access before relying on SSH. A host console can show boot output without providing an authenticated guest shell. If first-boot key injection fails before a console password was set, use the owned host's stopped-disk backup and cloud-init reseed procedure below. Never change a running guest disk offline or infer permission to access the host from guest SSH.

### Operation 1

```sh
# Linux HOST, after checking KVM and package/tool availability in level 1.
# Ubuntu host preparation if these tools are absent (owned host administrator only):
# sudo apt-get install qemu-kvm libvirt-daemon-system libvirt-clients virtinst cloud-image-utils
# Use sudo virsh consistently below. Do not grant a guest learner the host daemon socket.
sudo virsh -c qemu:///system net-list --all
# If the shipped default NAT network is inactive: sudo virsh -c qemu:///system net-start default
# If default does not exist, create a reviewed isolated NAT network before importing a guest.
mkdir -p work/vm
curl -fL https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img -o work/vm/noble-server-cloudimg-amd64.img
curl -fL https://cloud-images.ubuntu.com/noble/current/SHA256SUMS -o work/vm/SHA256SUMS
sha256sum work/vm/noble-server-cloudimg-amd64.img
# Compare with the exact noble-server-cloudimg-amd64.img entry in SHA256SUMS.
# Downloads over HTTPS plus a matched digest detect an incomplete/mismatched download;
# verify Ubuntu's signed checksum file as well when validating publisher provenance.
ssh-keygen -t ed25519 -f work/vm/relay-a-key
cp inputs/02/user-data work/vm/user-data
cp inputs/02/meta-data work/vm/meta-data
# In your editor replace the PUBLIC-key placeholder in work/vm/user-data; never paste the private key.
cloud-localds work/vm/seed.iso work/vm/user-data work/vm/meta-data
# This NEW directory is beneath the supported libvirt image path, not a private home directory.
sudo mkdir /var/lib/libvirt/images/ascend-lab
sudo qemu-img convert -O qcow2 work/vm/noble-server-cloudimg-amd64.img /var/lib/libvirt/images/ascend-lab/relay-a.qcow2
sudo qemu-img resize /var/lib/libvirt/images/ascend-lab/relay-a.qcow2 12G
sudo install -m 0644 work/vm/seed.iso /var/lib/libvirt/images/ascend-lab/seed-a.iso
# Ubuntu's QEMU service identity; inspect getent first if using a different distribution.
getent passwd libvirt-qemu
getent group kvm
sudo chown -R libvirt-qemu:kvm /var/lib/libvirt/images/ascend-lab
sudo virt-install --connect qemu:///system --name relay-a --memory 1024 --vcpus 1,maxvcpus=2 --import --disk path=/var/lib/libvirt/images/ascend-lab/relay-a.qcow2,format=qcow2 --disk path=/var/lib/libvirt/images/ascend-lab/seed-a.iso,device=cdrom --network network=default --osinfo detect=on,require=off --graphics none --noautoconsole
sudo virsh -c qemu:///system console relay-a
# Console escape: Ctrl+]. Cloud images generally have no password login: watch boot/cloud-init here.
# HOST: sudo virsh -c qemu:///system net-dhcp-leases default
# Connect with the public-key identity after verifying the guest fingerprint from trusted boot/console output.
# GUEST: cloud-init status --wait; hostname; ip -br address; sudo systemctl status ssh --no-pager
# GUEST: set a guest-local console recovery password with sudo passwd learner after key login.
# SSH password login remains disabled; retain the password privately and test the owned console path.
```

### Operation 2

```sh
# RECOVERY variant: OWNED HOST, for this newly created disposable guest only.
# First inspect boot output through virsh console and retain the original cloud-init input files.
# A console login prompt does not imply the cloud image has a usable password.
sudo virsh -c qemu:///system shutdown relay-a
sudo virsh -c qemu:///system domstate relay-a
# Do not continue until the guest is shut off. If this failed first-boot guest cannot obey ACPI shutdown,
# the explicit host force-stop is sudo virsh -c qemu:///system destroy relay-a (a forced power cut).
# Use that only for this disposable failed-first-boot target; keep its disk for diagnosis, not for a durability claim.
mkdir -p work/backups
sudo virsh -c qemu:///system dumpxml relay-a > work/backups/relay-a-before-reseed.xml
sudo qemu-img convert -O qcow2 /var/lib/libvirt/images/ascend-lab/relay-a.qcow2 work/backups/relay-a-before-reseed.qcow2
cp inputs/02/user-data work/vm/recovery-user-data
# Edit recovery-user-data: paste the exact existing operator PUBLIC key from work/vm/relay-a-key.pub.
# Keep ssh_pwauth false. Check YAML indentation, username and the assigned public key before rebuilding the seed.
printf 'instance-id: relay-a-reseed-01
local-hostname: relay-a
' > work/vm/recovery-meta-data
cloud-localds work/vm/recovery-seed.iso work/vm/recovery-user-data work/vm/recovery-meta-data
# With libguestfs-tools on the HOST, clear only the stopped guest's cloud-init cache; the backup stays untouched.
sudo virt-customize --add /var/lib/libvirt/images/ascend-lab/relay-a.qcow2 --run-command 'cloud-init clean --logs'
sudo install -o libvirt-qemu -g kvm -m 0644 work/vm/recovery-seed.iso /var/lib/libvirt/images/ascend-lab/seed-a-recovery.iso
sudo virsh -c qemu:///system domblklist relay-a
# Identify the actual CD-ROM target containing seed-a.iso (do not guess the primary disk target).
# Replace ACTUAL_SEED_CDROM_TARGET below with that observed CD-ROM target.
sudo virsh -c qemu:///system change-media relay-a ACTUAL_SEED_CDROM_TARGET --source /var/lib/libvirt/images/ascend-lab/seed-a-recovery.iso --update --config
sudo virsh -c qemu:///system start relay-a
sudo virsh -c qemu:///system console relay-a
# Re-check trusted boot/key output and DHCP address, then use the corrected public-key login.
# A changed server key after reseeding needs independent verification before updating that host's known_hosts entry.
# GUEST after key login: cloud-init status --wait; sudo passwd learner
# Test the new PRIVATE console password through the owned console while SSH still works.
# SSH password authentication remains disabled. Subsequent lockout practice can use this tested console login.
# This first-boot repair retains the original disk path; later resize/backup lessons still refer to that same guest.
```
